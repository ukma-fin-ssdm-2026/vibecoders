## 4. Співпраця та робочий процес
- Стратегія гілкування:
Ми використовуємо стратегію GitHub Flow, де головна гілка ⁠main⁠ є захищеною від прямих комітів, а для виконання кожного нового завдання створюються окремі тимчасові гілки з описовими префіксами ( ⁠feature/⁠, ⁠fix/⁠, ⁠docs/ тощо⁠)
- Практики комітів:
Дотримання принципу атомарності, де один коміт містить лише одну логічно завершену зміну, а повідомлення до нього завжди формулюються коротко та чітко пояснюють суть внесених оновлень.
- Правила огляду коду:
Усі злиття коду вимагають створення Pull Request та отримання принаймні 1 Approve від іншого учасника команди. Кожен PR обов’язково повинен успішно пройти автоматизовані перевірки GitHub Actions CI (на початковому етапі – успішне проходження базового тесту). Злиття неперевіреного коду в основну гілку заборонено. 
- Робочий процес завдань:
Завдання призначаються членам команди відповідно до ролі або за попередньою домовленістю після практичних та за потребою.
Завдання закривається тільки після відповідного PR.
