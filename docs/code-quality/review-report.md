# Звіт про огляд коду

**Команда:** Ctrl-Alt-Defeat (Movie Platform API)
 
## Три сильні сторони
1. Вхідні дані перевіряються через Pydantic, ліміти на пагінацію до 100. Некоректні дані не доходять до логіки.
2. Усі помилки мають однаковий формат. Зроблено через глобальні обробники, і він потрапляє в OpenAPI.
3. Документація гарно поєднується з кодом. OpenAPI генерується автоматично, pre-commit оновлює yaml, а сайт з документацією деплоїться на GitHub Pages. Окрім цього є ADR, модель загроз і матриця простежуваності.
## Три пропозиції щодо покращення
1. **CI -** зараз ci.yml просто робить echo, тому бейдж нічого не означає. Варто додати ruff і pytest. Немає requirements.txt і папки tests, без них CI нема з чим працювати.
2. **Структура коду -** моделі, обробники помилок, маршрути і mock_db лежать в одному main.py. Блок з 404 REVIEW_NOT_FOUND скопійований тричі. Краще розділити на schemas, errors, routers і окремий шар даних, а перевірку існування відгуку винести в одну функцію. У main.py має лишитись тільки ініціалізація, лишаємо створення FastAPI, підключення роутерів і обробників помилок.
3. **Стиль і docstrings -** довгі рядки, зайві пробіли в кінці рядків, немає docstrings у 9 класах і 8 функціях. Файл .gitignore зараз під C/Windows (*.obj, *.exe), для Python його треба переробити.

## Потенційна вразливість

**Немає автентифікації й авторизації:**
user_id береться з тіла запиту, тож можна створити відгук від чужого імені, patch і delete не перевіряють, чий це відгук, тому той, хто знає review_id, може змінити або видалити чужий відгук. А review_id віддається в GET /api/v1/reviews, тобто дізнатись його легко.

Що радимо зробити: додати авторизацію, брати user_id з токена, а в patch і delete перевіряти, що відгук належить користувачу, інакше віддавати 403. Токен не повинен бути вічним: треба задати exp, наприклад 15-30 хвилин, а для довшої сесії видавати refresh-токен. Тоді вкрадений токен буде небезпечним лише короткий час.

Дрібніші ризики: логів немає взагалі, а request_id ніде не записується.
