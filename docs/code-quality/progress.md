## 1. Що реалізовано

Файли модуля `src/api`:

- `main.py`, `schemas.py`, `security.py`, `errors.py`, `spec.py`, `generate_openapi.py`, `requirements.txt`
- сховище: `db.py` (підключення SQLAlchemy, SQLite), `models.py` (таблиці), `store.py` (проксі над БД, бронювання, хешування паролів, лічильник невдалих входів), `seed.py` (демо-дані)
- `routes/`: `auth.py` (вхід, реєстрація), `games.py`, `rooms.py` (календар, блокування на період), `users.py` (блокування акаунтів)
- `notifications.py`: сповіщення гравців про скасування гри (FR-011)
- `web/`: 8 сторінок інтерфейсу, `app.js`, `style.css`; сервер віддає їх на `/app/`
- `tests/`: 26 файлів (маршрути, схеми, безпека, сховище й БД, конкурентність, властивості, таблиця рішень, продуктивність, сповіщення, блокування кімнат, веб-інтерфейс, налаштування розгортання)

Поза `src/api`: `Dockerfile` і `render.yaml` (розгортання на Render), `scripts/check_traceability.py` (перевірка простежуваності в CI), `scripts/seed.py`.

**Працюючі компоненти, підтверджені тестами:** вхід і реєстрація (блокування після 5 невдалих спроб, SEC-003), ігри (створення, редагування, видалення, запис і вихід гравців), кімнати (календар, блокування на період з автоскасуванням ігор і сповіщенням гравців), блокування акаунтів власником, збереження даних у SQLite. Веб-інтерфейс `/app/` складається зі статичних сторінок, що викликають JSON API; тести перевіряють лише те, що сервер їх віддає.

**Сповіщення (`notifications.py`, FR-011):** при видаленні гри (`DELETE /api/v1/games/{id}`) функція `notify_game_cancelled` створює по одному сповіщенню для кожного записаного гравця. Вони зберігаються в таблиці `notifications` і перевірені тестами `test_notification.py`. Відправку листа через SMTP (Notification Service з `high-level-design.md`) додамо на наступних етапах.

## 2. Як запустити тести

З кореня репозиторію:

    python -m pytest

Конфігурація тестів лежить у `pytest.ini` (шлях до тестів: `src/api/tests`). Змінна середовища `PYTHONPATH` не потрібна.

Останній повний запуск (Python 3.12, pytest 8.4.2, команда з CI): 276 пройшли, 1 xfailed, покриття 96,32 % (поріг у CI 95 %). Нові тести цього етапу: `test_notification.py`, `test_quality_goals.py` (числові межі з `quality-attributes.md`), `test_db_models.py`, `test_concurrency.py`, `test_room_blocks.py`, `test_users_routes.py`, `test_web.py`, `test_deployment.py`.

## 4. Відгук від іншої команди (Team 3)

Звіт про наш код отримано. 

| Зауваження рецензентів | Рішення команди | 
| --- | --- | 
| Логувати спроби входу й додати тимчасове блокування після невдалих спроб | Блокування після 5 невдалих спроб реалізовано (SEC-003); логування спроб входу відкладено | 
| Додати `correlation_id` для трасування запитів | Відкладено до подальшого розвитку системи | 
| Додати чітку транзакційну межу між пов'язаними операціями | Частково: SQLite підключено ([ADR-004](../architecture/decisions/ADR-004.md)), перевірки й запис бронювань виконуються під `RLock`; повну транзакційну межу додамо з переходом на MySQL |
| race condition при PATCH | Доступ до БД захищено `RLock` (ADR-004); паралельне створення гри перевіряє `test_concurrency.py`, окремого тесту на паралельні PATCH немає | 

Сильні сторони, які відзначили рецензенти: розділення автентифікації й авторизації в `security.py` (`get_current_user`, `require_roles`), чітка структура роутів і схем, централізована обробка помилок без витоку деталей.

## 5. Відомі обмеження

- Сховище: один файл SQLite (`club.db`). Цього досить для демонстрації, але ціль — MySQL ([ADR-002](../architecture/decisions/ADR-002.md)), перехід не виконано. На безкоштовному Render файл лежить на тимчасовому диску й повертається до демо-даних після перезапуску.
- Лічильник невдалих входів (`LOGIN_FAILURES`) живе в пам'яті процесу й скидається при перезапуску. Час блокування акаунта (`locked_until`) зберігається в БД.
- Демо-токени (`master-token` тощо), демо-паролі та небезпечна сіль за замовчуванням (`PASSWORD_SALT`) є в коді й на сторінці входу. Для публічного стенду ризик прийнято, див. `static-analysis.md`, розділ 4.
- Відомий дефект D-1: `GET /api/v1/games/{id}/players` доступний будь-якому автентифікованому користувачу, а Test-17 і SEC-002 вимагають доступу лише майстра гри та власника клубу. Тест `test_list_players_forbidden_for_player_who_does_not_run_the_game` позначено `xfail`.
- Інтерфейс — статичні HTML-сторінки з JavaScript. Серверний рендеринг (Jinja2 і HTMX) з ADR-001 не реалізовано, а поведінку сторінок у браузері тести не перевіряють.
- Не реалізовано: відправка листів (SMTP), завантаження аватара, вимір доступності (REL-003), перевірка зручності на групі 8-10 користувачів (USAB-001), зміна кімнат без передеплою (MAINT-001).
