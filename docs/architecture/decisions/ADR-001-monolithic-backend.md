# ADR 001: Вибір монолітної клієнт-серверної архітектури з HTMX та MySQL

**Дата:** 01.10.2026
**Статус:** Прийнято

## Контекст
Команді з 4 студентів необхідно розробити веб-платформу для організації НРІ з функціями запису гравців та бронювання кімнат. На рішення тиснуть наступні вимоги: жорсткі академічні терміни розробки, необхідність 100% уникнення подвійного бронювання однієї кімнати (овербукінг) та відсутність складного інтерактивного UI, окрім календаря. 

## Рішення
Використовувати класичну багатошарову монолітну архітектуру. Як бекенд використовується мікрофреймворк FastAPI. Інтерфейс рендериться на сервері (SSR) за допомогою шаблонів Jinja2, а динамічність забезпечується бібліотекою HTMX (AJAX-запити за HTML-фрагментами). База даних — реляційна (MySQL).

## Наслідки
- **Плюси:** Значне скорочення часу на розробку (немає потреби у JS-фреймворках). Висока узгодженість даних: транзакції MySQL на рівні єдиного бекенду надійно блокують подвійні бронювання кімнат.
- **Застереження:** Оскільки клієнт і сервер тісно пов'язані, необхідно суворо дотримуватися організації структури Jinja2-шаблонів, щоб код не перетворився на "кашу".
- **Мінуси:** Якщо в майбутньому виникне вимога розробити нативний мобільний застосунок (iOS/Android), нам доведеться писати окремий REST API, оскільки поточна система віддає HTML-розмітку, а не чисті JSON-дані.

## Розглянуті альтернативи
1. **Мікросервісна архітектура:** Відхилено. Вимагає складного налаштування інфраструктури (DevOps, CI/CD для кожного сервісу), що є оверінжинірингом для простого CRUD-додатка та команди з 5 студентів.
2. **Розділений REST API + React SPA:** Відхилено. Розробка окремого фронтенду вимагає дублювання логіки маршрутизації, налаштування CORS та підтримки двох репозиторіїв/пайплайнів. Це збільшило б час розробки, тоді як HTMX дозволяє реалізувати ту саму динаміку календаря простіше.

*Використання ШІ: структура документу, базові формулювання та код PlantUML згенеровані за допомогою ШІ. Матеріали були вичитані, проаналізовані Керівником архітектури та повністю адаптовані командою під обрану бізнес-логіку проєкту для відповідності критеріям оцінювання Лабораторної роботи.*
