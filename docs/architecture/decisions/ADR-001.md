# ADR-001: Архітектурний стиль — моноліт із серверним рендерингом (FastAPI + Jinja2 + HTMX)

## Статус
Прийнято — 2026-10-01

## Контекст
Команда з 4 осіб розробляє систему для одного клубу НРІ за один семестр. Функціональні вимоги FR-001–FR-007 — це переважно CRUD над іграми й бронюваннями та відображення календаря, без складної real-time взаємодії між багатьма користувачами одночасно. Найбільше тиснуть на вибір стилю:

- **USAB-001** — реєстрація та перша заявка на гру повинні займати ≤3 хв без звернення до довідки;
- **MAINT-001** — зміна кількості/місткості кімнат — без перекомпіляції чи передеплою коду;
- **C-001** — це веб-сайт; окремих мобільних застосунків у цій версії не передбачено;
- **REL-001 / REL-002** — подвійне бронювання кімнати і перетин ігор одного майстра мають виключатися гарантовано, в ідеалі — в межах однієї транзакції БД, без розподілених викликів.

Команда також має різний рівень досвіду у фронтенд-розробці (розподіл ролей у TeamCharter орієнтований на бекенд/CI/документацію), тож рішення, що мінімізує обсяг клієнтського JavaScript, знижує ризик для проєкту.

## Рішення
Використовувати монолітний бекенд на **FastAPI** із серверним рендерингом HTML через **Jinja2**, де динамічні фрагменти сторінки (статус слотів календаря, лічильник вільних місць) оновлюються бібліотекою **HTMX** — замість окремого SPA-фронтенду (React/Vue) з REST/JSON API або декомпозиції системи на мікросервіси.

## Наслідки

**Переваги**
- Один репозиторій і один процес розгортання — менше DevOps-навантаження на команду з 4 студентів.
- Немає окремого JSON API-контракту для проєктування, підтримки й версіонування — швидша розробка в межах семестру.
- REL-001/REL-002 простіше гарантувати: перевірка і резервування кімнати відбуваються в одній транзакції MySQL, без розподілених викликів між сервісами.
- Менша поверхня атаки: немає публічного JSON API, яким міг би скористатися довільний сторонній клієнт.

**Застереження**
- UI-логіку складніше тестувати ізольовано від розмітки (перевірка йде по HTML-фрагменту, а не по чистій структурі даних) — прийнятно через невеликий обсяг UI-логіки в проєкті.
- Частина поведінки все одно виконується в браузері (HTMX AJAX-запити), тож налагодження іноді вимагає інструментів розробника в браузері, а не лише серверних логів.

**Мінуси**
- Додати окремий мобільний застосунок чи стороннього API-клієнта пізніше означатиме проєктувати повноцінний JSON API з нуля (зараз свідомо поза межами, C-001).
- Багаті клієнтські взаємодії (наприклад, перетягування подій у календарі) реалізувати на HTMX незручніше, ніж на повноцінному SPA-фреймворку.
- Горизонтальне масштабування моноліту грубіше: неможливо масштабувати Room Booking Service окремо від решти системи — прийнятно при масштабі одного клубу з 3 кімнатами (A-001), але обмежує майбутнє зростання.

## Розглянуті альтернативи
1. **SPA (React/Vue) + REST/JSON API.** Відхилено: окремий білд-пайплайн фронтенду і проєктування API-контракту не вкладаються в ресурс команди за семестр; JSON API додає поверхню атаки (потрібна токен-автентифікація) без очевидної вигоди, якщо мобільний застосунок не планується (C-001).
2. **Мікросервіси** (Auth/Game/Booking як окремі незалежно розгорнуті процеси). Відхилено: операційна складність (мережеві виклики, розподілені транзакції) непропорційна масштабу системи (один клуб, 3 кімнати); REL-001 значно простіше гарантувати в межах однієї БД-транзакції, ніж між сервісами.
3. **Serverless-функції** на кожен ендпоїнт. Відхилено: холодний старт конфліктує з очікуваннями швидкодії, а стале з'єднання з БД, потрібне для блокування рядків (`SELECT ... FOR UPDATE`, REL-001), погано поєднується із serverless-моделлю виконання.

Створено з допомогою ШІ, перевірено прочитанням та порівнянням з реальністю.
