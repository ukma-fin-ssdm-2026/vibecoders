# ADR-002: Вибір бази даних — реляційна MySQL замість NoSQL

## Статус
Прийнято — 2026-10-01

## Контекст
Найкритичніші нефункціональні вимоги системи — **REL-001** (20 одночасних спроб забронювати один часовий слот кімнати не повинні дати жодного дубля) і **REL-002** (один майстер не може вести дві гри, що перетинаються в часі). Обидві вимагають атомарної, узгодженої перевірки над строго структурованими, пов'язаними даними (кімнати, часові слоти, ігри, користувачі), а кожне бронювання завжди посилається на конкретну існуючу кімнату й гру (цілісність зовнішніх ключів). **FR-005** (інтерактивний календар зайнятості 3 кімнат клубу) також природно виражається через реляційні вибірки з `JOIN`.

## Рішення
Зберігати дані системи в реляційній СУБД **MySQL** з ACID-транзакціями (блокування рядків `SELECT ... FOR UPDATE` під час перевірки й резервування кімнати) через ORM **SQLAlchemy** — замість документоорієнтованої чи key-value NoSQL бази даних.

## Наслідки

**Переваги**
- Гарантії узгодженості транзакцій напряму покривають REL-001/REL-002 без потреби в додатковій інфраструктурі розподілених блокувань.
- Зовнішні ключі безкоштовно забезпечують цілісність зв'язків користувач–гра–кімната–бронювання.
- SQL/`JOIN` природно підходить для вибірок календаря і доступності кімнат (FR-005).
- Зріла екосистема (SQLAlchemy, міграції Alembic, великий обсяг навчальних матеріалів) — важливо для студентської команди, що вчиться по ходу проєкту.

**Застереження**
- Зміни схеми вимагають міграцій — трохи більше дисципліни на етапі проєктування, ніж у безсхемній NoSQL-базі.
- Вертикальні обмеження масштабування існують у принципі, але неактуальні при A-001 (клуб завжди має рівно 3 кімнати).

**Мінуси**
- Під високим конкурентним навантаженням на один і той самий слот блокування рядків може серіалізувати частину запитів і додати затримку в пікові моменти запису — пом'якшується тим, що транзакція охоплює лише вузьку перевірку-й-вставку бронювання, а не весь запит цілком.

## Розглянуті альтернативи
1. **MongoDB** (документоорієнтована). Відхилено: немає нативних багатодокументних ACID-транзакцій у звичній для команди формі; реляційні зв'язки (доступність кімнати між різними іграми) незручно моделювати документами, а гарантію "жодного дубля" важче зробити надійною без реляційних обмежень і блокувань на рівні СУБД.
2. **Redis** як основне сховище даних. Відхилено: за замовчуванням не гарантує довговічність (persistence) даних, що неприйнятно для записів про бронювання клубу; може розглядатися пізніше як кеш перед MySQL, але не як основна база даних.
3. **SQLite.** Відхилено для виробничого середовища, попри найпростіше налаштування: однописьмова модель доступу на рівні файлу погано витримує конкурентний запис, що напряму підриває гарантію REL-001 про 20 одночасних спроб без дублів; прийнятний лише для локальної розробки й тестів.
