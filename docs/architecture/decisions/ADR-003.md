# ADR-003: Автентифікація — серверні сесії замість JWT

## Статус
Прийнято — 2026-10-01

## Контекст
**FR-001** вимагає розділення прав доступу між ролями (Майстер / Гравець / Адміністратор-власник клубу). **SEC-003** вимагає автоматичного блокування акаунта на 15 хв після 5 послідовних невдалих спроб входу за 15 хв, а **US-004** вимагає, щоб власник клубу міг миттєво заблокувати акаунт порушника. Згідно з ADR-001, система — серверно-рендерений моноліт без окремого публічного JSON API, а **C-001** виключає окремий мобільний застосунок, якому був би потрібен портативний токен доступу.

## Рішення
Автентифікувати користувачів через **серверну сесію**: ідентифікатор сесії зберігається в HttpOnly-кукі браузера, а стан самої сесії — на сервері (таблиця сесій у MySQL), замість самодостатніх (stateless) **JWT**-токенів.

## Наслідки

**Переваги**
- Сесію можна миттєво анулювати на сервері — критично для SEC-003 (блокування після невдалих спроб) і US-004 (власник блокує акаунт): заблокований JWT лишався б дійсним до завершення терміну дії, якби не було окремого списку відкликання.
- HttpOnly-кукі простіше захистити від XSS, ніж токен, доступний клієнтському JavaScript.
- Природно поєднується з серверним рендерингом (ADR-001): браузер автоматично надсилає кукі з кожним HTMX-запитом, не потрібно вручну прикріплювати заголовок `Authorization`.

**Застереження**
- Потрібне серверне сховище сесій — невеликий, але все ж додатковий стан (таблиця сесій), а не повністю stateless-сервер.
- Якщо систему колись доведеться масштабувати на кілька інстансів бекенду, сховище сесій має стати спільним (MySQL чи, наприклад, Redis), а не пам'яттю одного процесу — прийнятно зараз при розгортанні на одній виробничій машині (див. deployment-diagram).

**Мінуси**
- Підхід погано підходить для гіпотетичного майбутнього мобільного застосунку чи стороннього API-клієнта, які зазвичай очікують токен-автентифікацію — узгоджено з поточним C-001, але вимагатиме перегляду цього ADR, якщо це припущення зміниться.

## Розглянуті альтернативи
1. **JWT (stateless bearer-токени).** Відхилено: миттєве відкликання (потрібне для SEC-003 і US-004) вимагало б окремого списку відкликаних токенів, що повертає серверний стан назад, не даючи натомість переваги для односерверного веб-застосунку.
2. **OAuth2 / сторонній вхід (Google, GitHub SSO).** Відхилено для цієї версії: додає зовнішню залежність і налаштування поза обсягом семестрового проєкту; вимоги не передбачають соціального входу, реєстрації через пошту НаУКМА достатньо.
3. **Без збереження сесії** (повторна автентифікація на кожен запит). Відхилено: прямо суперечить USAB-001 (швидка, беззаперечна реєстрація і перша заявка на гру за ≤3 хв).
