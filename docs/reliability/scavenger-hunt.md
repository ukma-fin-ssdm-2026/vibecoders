## R-01. Необроблений виняток зникає без сліду (A, D)

```python
@app.exception_handler(Exception)
async def unexpected_error_handler(request: Request, exc: Exception):
    return error_response(500, "INTERNAL_ERROR", "Внутрішня помилка сервера")
```

**Чому небезпечно.** Користувач справді не бачить внутрішніх деталей, і це добре. Але розробник теж їх не бачить: причина 500 ніде не записується. Будь-яка інша знахідка з цього списку проявляється саме так.
**Потенційний вплив.** Збій у продакшні (Render) неможливо діагностувати. Повторюваний баг може тижнями виглядати як «іноді падає».

| Поле | Значення |
|------|----------|
| Несправність | обробник `Exception` не пише в лог |
| Помилка | виняток перехоплено, внутрішній стан втрачено |
| Відмова | клієнт отримує 500, команда не знає чому |
| Критичність | Висока |

## R-02. Сповіщення про скасування створюються після коміту, поза транзакцією (D)

```python
            db.commit()
        finally:
            db.close()

    for game_id, title, players in notifications:
        GAMES._cache.pop(game_id, None)
        notify_game_cancelled(game_id, title, players)
```

**Чому небезпечно.** `POST /rooms/{id}/blocks` видаляє ігри й створює блокування в одній транзакції, а сповіщення пише окремою транзакцією після неї. Якщо запис сповіщень падає (БД зайнята, диск), ігри вже видалені, блокування створене, а гравці нічого не дізналися.
**Потенційний вплив.** Гравці приходять на гру, якої вже немає. Клієнт отримує 500 і може повторити запит, але повтор дасть 409 `ROOM_BLOCK_CONFLICT`, бо блокування вже існує, тож сповіщення втрачено назавжди.

Відтворено на коді до виправлення (інжектований збій запису сповіщень): відповідь 500, `game_1` видалена (404), блокування створене, сповіщень 0.

| Поле | Значення |
|------|----------|
| Несправність | дві незалежні транзакції для однієї бізнес-операції |
| Помилка | БД у стані «гру скасовано, гравців не повідомлено» |
| Відмова | гравці не знають про скасування; повтор запиту неможливий |
| Критичність | Висока |

## R-03. Видалення гри не атомарне і виконується без блокування (D, E)

```python
    record = get_game_or_404(game_id)
    ensure_can_manage(record, user.id, user.role)
    notify_game_cancelled(game_id, record.title, ENROLLMENTS.get(game_id, []))
    del GAMES[game_id]
    ENROLLMENTS.pop(game_id, None)
```

**Чому небезпечно.** Три кроки в трьох окремих транзакціях, і всі без `db_lock` (інші зміни стану його беруть). Порядок «спершу сповістити, потім видалити» означає, що збій на видаленні залишає гру живою, а гравці вже отримали «гру скасовано». Гравець, що записався між читанням списку і видаленням, сповіщення не отримає.
**Потенційний вплив.** Хибні сповіщення про скасування, або гравці без сповіщень.

Відтворено на коді до виправлення (інжектований збій видалення): відповідь 500, `game_1` існує (200), а сповіщення для `user_2` вже створене.

| Поле | Значення |
|------|----------|
| Несправність | кілька записів у різних транзакціях, немає блокування |
| Помилка | сповіщення і стан гри розійшлися |
| Відмова | користувач бачить «гру скасовано», а гра в розкладі є |
| Критичність | Висока |

## R-04. Скасування запису гравця: «прочитати, змінити, перезаписати» без блокування (E)

```python
    players = ENROLLMENTS.get(game_id, [])
    remaining = [p for p in players if p.user_id != user_id]
    ...
```

**Чому небезпечно.** `ENROLLMENTS[game_id] = ...` видаляє всі записи гри і створює їх заново зі списку, прочитаного раніше (`store.py:230-238`). Якщо між читанням і записом хтось записався (`enroll_player` працює під `db_lock`, а `remove_player` ні), його запис зникає.

| Відмова | підтверджений запис мовчки зникає |

## R-05. З'єднання з БД без явного тайм-ауту; налаштування мовчки перекрите (B)

```python
engine = configure_engine(
    create_engine(DATABASE_URL, connect_args={"check_same_thread": False, "timeout": 30} if _is_sqlite else {})
)
...
engine = create_database_engine(str(DATABASE_URL))
```

**Чому небезпечно.** У `db.py` двічі визначені `resolve_database_url`, `engine` і `DATABASE_URL`. Другий `engine` (рядок 94, без `timeout`) замінює перший (рядок 52, з `timeout: 30`), тому коментар «паралельні записи чекали, а не падали» описує мертвий код. Реальний тайм-аут дорівнює вбудованому значенню `sqlite3` (5 с) і ніде не налаштовується. При навантаженні запис падає з `database is locked`.
**Потенційний вплив.** Короткочасне блокування БД перетворюється на 500 для користувача; поведінку не можна підкрутити без правки коду.

| Поле | Значення |
|------|----------|
| Несправність | немає явного, налаштовуваного тайм-ауту; дубльовані визначення перекривають одне одного |
| Помилка | `OperationalError: database is locked` |
| Відмова | 500 замість зрозумілої відповіді «спробуйте пізніше» |
| Критичність | Середня |

## R-06. Недоступність БД не відрізняється від програмної помилки (A, B)
