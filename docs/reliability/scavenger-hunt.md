## 1. Знахідки

### R-01. Обробник 500 нічого не логує (A, D)

```python
    @app.exception_handler(Exception)
    async def unexpected_error_handler(request: Request, exc: Exception):
        return error_response(500, "INTERNAL_ERROR", "Внутрішня помилка сервера")
```

**Чому небезпечно:** відповідь для користувача безпечна (без внутрішніх деталей), але причина збою не потрапляє ніде. Розібратися, що сталося, неможливо.
**Потенційний вплив:** будь-яка непередбачена помилка стає «невидимою»; діагностика інцидентів у продакшні практично неможлива.

### R-02. Сповіщення про скасування пишуться після коміту, поза транзакцією (D)

```python
            db.commit()
        finally:
            db.close()

    for game_id, title, players in notifications:
        GAMES._cache.pop(game_id, None)
        notify_game_cancelled(game_id, title, players)
```

**Чому небезпечно:** ігри вже видалені й закомічені, а сповіщення створюються окремим кроком. Якщо запис сповіщень падає, зміна не відкочується.
**Потенційний вплив:** блокування кімнати скасувало ігри, а гравці про це не дізналися; база в неузгодженому стані.

### R-03. Видалення гри: три окремі транзакції, без `db_lock`, сповіщення до видалення (D, E)

```python
    record = get_game_or_404(game_id)
    ensure_can_manage(record, user.id, user.role)
    notify_game_cancelled(game_id, record.title, ENROLLMENTS.get(game_id, []))
    del GAMES[game_id]
    ENROLLMENTS.pop(game_id, None)
    return Response(status_code=204)
```

**Чому небезпечно:** сповіщення надсилається до видалення, а кроки не атомарні й не захищені блокуванням, на відміну від інших змінюючих запитів.
**Потенційний вплив:** гравці отримують сповіщення про скасування гри, яка після збою лишилась; паралельний запис на гру губиться.

### R-04. `remove_player`: читання-зміна-запис без блокування (E)

```python
    players = ENROLLMENTS.get(game_id, [])
    remaining = [p for p in players if p.user_id != user_id]
    ...
    ENROLLMENTS[game_id] = remaining
    return Response(status_code=204)
```

**Чому небезпечно:** між читанням списку й записом іншого запит може додати гравця; запис `remaining` перезапише чужу зміну.
**Потенційний вплив:** втрата запису іншого гравця на гру без жодної помилки.

### R-05. З'єднання SQLite без явного тайм-ауту (B)

```python
        connect_args={"check_same_thread": False} if url.get_backend_name() == "sqlite" else {},
```

**Чому небезпечно:** залежність від прихованого значення за замовчуванням (5 с у `sqlite3`), яке не можна налаштувати. У `db.py` також були дубльовані визначення.
**Потенційний вплив:** під навантаженням запити чекають на заблоковану БД невизначено для оператора; налаштувати поведінку без зміни коду неможливо.
**Статус:** виправлено. Налаштовано явний тайм-аут `DB_TIMEOUT_SECONDS = 10.0` с та захисне зчитування, а дубльовані визначення функцій і engine остаточно усунуто в гілці `fix/db-duplicate-definitions`.

### R-06. `OperationalError` потрапляє в загальний 500 без `Retry-After` (A, B)

Той самий `unexpected_error_handler` з R-01 обробляв і збій БД.

**Чому небезпечно:** тимчасова недоступність БД виглядає для клієнта як внутрішня помилка сервера; немає підказки, що можна повторити запит.
**Потенційний вплив:** клієнти не відрізняють «повторіть пізніше» від «зламано назавжди»; зайві звернення в підтримку.

### R-07. Збій запису OpenAPI-файлу при старті валить увесь сервіс (B)

```python
    seed_db()
    save_openapi_spec(app)
    yield
```

**Чому небезпечно:** допоміжна функція (збереження документації у файл) не обгорнута обробкою помилок, тож `OSError` зупиняє старт.
**Потенційний вплив:** API не стартує через недоступну для запису теку `docs/api/`, хоча для користувачів документація необов'язкова.

### R-08. Блокувальний ввід-вивід і pbkdf2 в `async def` (E)

```python
async def login(payload: LoginRequest):
    ...
    if account is None or not verify_password(payload.password, account["password_hash"]):
```

```python
def hash_password(password: str) -> str:
    return hashlib.pbkdf2_hmac("sha256", password.encode("utf-8"), PASSWORD_SALT, 100_000).hex()
```

**Чому небезпечно:** `async def` без `await` виконується в потоці подій; хешування pbkdf2 (100 000 ітерацій) і синхронні звернення до БД блокують усі інші запити. Те саме стосується більшості обробників у `routes/`.
**Потенційний вплив:** кілька одночасних входів сповільнюють або «заморожують» увесь API.
**Статус:** виправлено (Ж). Усі обробники в `routes/` переведено з `async def` на `def`: FastAPI виконує їх у пулі потоків, тож pbkdf2 і запити до БД більше не зупиняють цикл подій. Перевіряє `test_reliability_sync_handlers.py`.

### R-09. Лічильник невдалих входів у пам'яті, без блокування (D, E)

```python
def register_failed_login(email: str, now: datetime) -> None:
    recent = [t for t in LOGIN_FAILURES.get(email, []) if now - t < LOGIN_WINDOW]
    recent.append(now)
    if len(recent) >= MAX_FAILED_LOGINS:
        LOCKED_UNTIL[email] = now + LOCK_DURATION
        LOGIN_FAILURES.pop(email, None)
    else:
        LOGIN_FAILURES[email] = recent
```

**Чому небезпечно:** стан живе лише в пам'яті процесу: перезапуск або кілька воркерів скидають або розділяють лічильник; паралельні спроби гублять записи.
**Потенційний вплив:** захист від підбору пароля легко обійти (перезапуск, паралельні запити).
**Статус:** виправлено (З). Невдалі входи зберігаються в таблиці `login_failures`; `store.record_failed_login` додає запис, перевіряє ліміт і виставляє `locked_until` в одній транзакції під `db_lock`. Збій запису піднімається як `OperationalError` і дає 503, а не мовчазно пропущену спробу. Перевіряє `test_reliability_login_lockout.py`.

### R-10. `int(...)` над id з БД без перевірки формату (C)

Фрагмент до виправлення в PR #212:

```python
                (int(user_id.removeprefix("user_")) for (user_id,) in existing_ids if user_id.startswith("user_")),
```

**Чому було небезпечно до PR #212:** якщо в БД потрапить id на кшталт `user_abc`, `int()` кине `ValueError`. Перевірка `isdigit()` у генераторі ID ігор також недостатня: вона приймає Unicode-цифри, зокрема ті, які `int()` не може перетворити.
**Потенційний вплив до виправлення:** реєстрація нових користувачів могла перестати працювати через один некоректний запис; некоректний ID гри також міг зірвати генерацію наступного ID.
**Статус:** виправлено в PR #212: спільний `_numeric_id_suffix` приймає лише ASCII-цифри для ID користувачів та ігор. `test_registration_ignores_malformed_id_suffixes` перевіряє `user_abc`, `user_`, `user_1a` та Unicode-суфікси; `test_next_game_id_ignores_malformed_id_suffixes` перевіряє `game_abc` і Unicode-суфікси. Старий код уже безпечно ігнорував `game_abc`; цей випадок фіксує очікувану поведінку, а не відтворює регресію.

### R-11. Мовчазне резервне значення `PASSWORD_SALT` (D)

Фрагмент до виправлення в PR #212:

```python
PASSWORD_SALT = os.getenv("PASSWORD_SALT", "default-insecure-salt-for-dev").encode("utf-8")
```

**Чому було небезпечно до PR #212:** якщо змінну забули налаштувати в продакшні, сервіс тихо працював із відомою сіллю, без попередження в логах.
**Потенційний вплив до виправлення:** слабший захист паролів без жодного сигналу; змінити сіль пізніше означає інвалідувати всі наявні хеші.
**Статус:** виправлено в PR #212: `APP_ENV=production` без `PASSWORD_SALT` завершує запуск із явною помилкою; development використовує попередження й попередній fallback для локальної сумісності. Render задає `APP_ENV=production` і генерує сіль.

### R-12. `fetch` у фронтенді без тайм-ауту (B)

```javascript
      try {
        response = await fetch('/api/v1' + cleanPath, options);
      } catch (networkErr) {
```

**Чому небезпечно:** мережеву помилку оброблено, але якщо сервер не відповідає (наприклад, «засинає» на хостингу), запит висить без обмеження за часом.
**Потенційний вплив:** користувач бачить нескінченне завантаження і не отримує повідомлення про проблему.
**Статус:** виправлено (И). `App.api` скасовує запит через `AbortController` після `App.API_TIMEOUT_MS` (15 с), включно з читанням тіла відповіді, і кидає помилку з кодом `TIMEOUT`. Перевіряє `test_reliability_frontend.py` (реальний `app.js` у Node.js).

### R-13. `getMe` повертає `null` для будь-якої помилки (D)

```javascript
      try {
        var user = await App.api('GET', '/users/me');
        if (user && user.id) {
          ...
          return user;
        }
        return null;
      } catch (err) {
        return null;
      }
```

**Чому небезпечно:** 401 (потрібен вхід), 503 (сервер недоступний) і мережевий збій дають однаковий результат; причина губиться без логування.
**Потенційний вплив:** під час збою сервера користувача можуть переправити на сторінку входу, ніби його сесія недійсна.
**Статус:** виправлено (И). `getMe` повертає `null` лише без сесії або при 401; 503, `TIMEOUT` і мережевий збій логуються через `console.error` і передаються викликачу. `admin.html` показує причину замість мовчазного продовження.

### R-14. Повне сканування ігор під `db_lock` (E)

```python
    records = sorted_games(list(GAMES.values()))
    if room_id:
        records = [r for r in records if r.room_id == room_id]
    if master_id:
        records = [r for r in records if r.master_id == master_id]
    page = records[offset : offset + limit]
```

**Чому небезпечно:** кожен запит завантажує й сортує всі ігри, а потім відфільтровує в Python.
**Потенційний вплив:** час відповіді росте разом з кількістю ігор; за поточного обсягу даних проблема непомітна.
**Статус:** виправлено (І). `store.query_games` фільтрує, сортує й нарізає сторінку в БД; `find_busy_game` бере лише ігри потрібної кімнати або майстра; `room_has_games` перевіряє наявність одним запитом. Перевіряє `test_reliability_game_queries.py`.

### R-15. Кеш проксі без меж і з ручною інвалідацією (D)

```python
            db.commit()
            self._cache[key] = value
```

**Чому небезпечно:** кеш (`self._cache`) не має обмеження розміру, а скидається вручну в окремих місцях (наприклад, `GAMES._cache.pop(game_id, None)`). Забута інвалідація дає застарілі дані.
**Потенційний вплив:** користувач бачить застарілий стан гри; пам'ять повільно зростає.
**Статус:** виправлено (Ї). Кеш замінено на `BoundedCache` (LRU, 1024 записи). Значення завжди перебудовується з рядка БД, а закешований об'єкт повертається лише якщо він йому дорівнює, тому застарілі дані неможливі, а ручну інвалідацію замінено єдиним методом `invalidate`. Перевіряє `test_reliability_cache.py`.

## 2. Класифікація: несправність → помилка → відмова

Ланцюги в таблиці описують стан до виправлення; актуальний статус кожної проблеми наведено в розділі 3.

|----|----------------------|-----------------|--------------------|-------------|

| R-09 | Лічильник спроб тримається лише в пам'яті без блокування | Лічильник скинуто або перекручено | Підбір пароля не блокується | Середня |

| R-11 | Резервне значення солі без попередження | Сервіс працює з відомою сіллю | Слабший захист паролів (потенційна відмова безпеки) | Середня |
| R-12 | `fetch` без `AbortController` і тайм-ауту | Запит висить без завершення | Нескінченне завантаження сторінки | Середня |

Для R-02 і R-03 ланцюг відтворено вручну на старому коді (див. розділ 5 звіту): блокування кімнати дало 500, гру видалено, блокування створено, сповіщень 0.
