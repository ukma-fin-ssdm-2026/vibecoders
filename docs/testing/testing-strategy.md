# Стратегія тестування (Testing Strategy)

## 1. Поточний статус тестування
На даному етапі реалізовано комплексний набір модульних тестів (Unit Tests) для ключових компонентів системи (`src/api`). Тестування охоплює всі основні маршрути (автентифікація, ігри, кімнати), перевірку схем (Pydantic), безпекові функції та модулі доступу до даних. Для ізольованої перевірки бізнес-логіки активно використовуються тестові дублери (моки та заглушки in-memory сховища) і фікстури (`conftest.py`).

## 2. Підсумок покриття
- **Загальний відсоток:** 99.48%.
- **Що залишилося непокритим і чому:** Непокритими залишилися близько 0.5% коду. Здебільшого це блоки перехоплення системних винятків (наприклад, збої на рівні конфігурації сервера Uvicorn) та фрагменти коду, які обробляють критичні помилки інфраструктури (до яких складно написати ізольовані модульні тести без складних моків). Для поточного етапу це прийнятний рівень.

## 3. Інтеграція в CI/CD
Тестування повністю інтегровано у наш конвеєр безперервної інтеграції (GitHub Actions). При створенні Pull Request автоматично запускається лінтинг (Black, Flake8), аналіз безпеки (Bandit) та набір тестів Pytest із вимірюванням покриття (`pytest-cov`). Збірка вважається неуспішною, якщо покриття падає нижче встановленого порогу (95%).

## 4. Плани для наступних рівнів тестування
- **Інтеграційні тести:** Після впровадження реальної реляційної бази даних (MySQL) ми плануємо додати тести, які перевірятимуть коректність SQL-транзакцій, взаємодію з базою даних та дотримання властивостей ACID при бронюваннях.
- **Системні тести (E2E):** У майбутньому планується впровадження наскрізного тестування (наприклад, за допомогою Playwright) для перевірки повного циклу роботи користувача: від клієнтського веб-інтерфейсу до бази даних.
- **Приймальні тести (UAT):** Планується проведення сесій тестування з реальними користувачами (Майстрами та Гравцями) для валідації вимог до зручності використання (UX/UI).

## 5. Плани для специфічних видів тестування
- **Тестування продуктивності:** Використання навантажувального тестування (наприклад, Locust) для симуляції десятків одночасних спроб бронювання однієї кімнати, щоб переконатися у відсутності стану гонитви (race conditions).
- **Property-based тестування:** Бібліотека Hypothesis вже використовується для перевірки властивостей часових інтервалів. Плануємо розширити її застосування для автоматичної валідації вхідних даних API (генерація випадкових JSON-payloads).

## Бонуси

### Ворота покриття в CI

- **Що зроблено:** тести з вимірюванням покриття запускаються в CI на кожен pull request у `main` (і на push у `main` та `feature/*`). Збірка падає, якщо покриття нижче порога.
- **Поріг:** 95% (`--cov-fail-under=95`).
- **Чому такий:** покриття на момент написання документу 99.48%; поріг на 4.48 нижче, щоб не блокувати дрібні зміни, але не допускати помітного зниження покриття.
- **Де налаштовано:** `.github/workflows/ci.yml`, крок «Run tests with Pytest and coverage»; конфігурація покриття в `.coveragerc`.
- **Успішний прогін:** https://github.com/ukma-fin-ssdm-2026/vibecoders/actions/runs/39595344779

### Мутаційне тестування

Інструмент: mutmut 3. Він доданий у `src/api/requirements.txt` з умовою `python_version >= "3.10"`, бо CI працює на Python 3.9, а mutmut 3 вимагає 3.10 або новішу. Модуль: `src/api/store.py`. Запуск: `bash scripts/run_mutation.sh`.

Останній прогін: 68 мутантів, 66 вбито, 2 вижили, оцінка мутації 97,1%. Раніше тут було 57 мутантів, число змінилося, бо ми запускали заново, тому далі рахуємо за новим прогоном.

**Мутант, що вижив без тесту і загинув з тестом.** У функції `find_busy_game` оператор `continue` (пропуск гри, яку редагують) mutmut замінює на `break`. Це мутант `store.x_find_busy_game__mutmut_4`.

1. Без тесту: `MUTATION_WITHOUT_TEST=test_find_busy_game_skips_excluded_game_and_still_finds_later_conflict bash scripts/run_mutation.sh`. Скрипт копіює проєкт у тимчасову папку і прибирає цей тест тільки там, у репозиторії він лишається. Результат: `store.x_find_busy_game__mutmut_4: survived`, а також два еквівалентні мутанти нижче. Зміну видно командою `python -m mutmut show store.x_find_busy_game__mutmut_4` (у робочій папці, її шлях друкується в кінці): `continue` стало `break`.
2. З тестом: `bash scripts/run_mutation.sh`. Той самий мутант `store.x_find_busy_game__mutmut_4: killed`, виживають лише два еквівалентні.

Чому тест його вбиває: у ньому гра, що редагується, стоїть у списку першою, а справжній конфлікт іде після неї. З `continue` функція пропускає редаговану гру і знаходить конфлікт, з `break` цикл зупиняється одразу і повертає `None`.

Тест `test_find_busy_game_skips_excluded_game_and_still_finds_later_conflict` ми закомітили раніше, ніж налаштували скрипт mutmut, тому в історії комітів порядок зворотний. Щоб показати зв'язок мутанта і тесту, ми додали в скрипт змінну `MUTATION_WITHOUT_TEST`.

Другий приклад: `and` замінено на `or` у перевірці майстра (`same_master`). Додано `test_find_busy_game_ignores_games_of_other_master`.

Два мутанти, що лишилися (`"sha256"` → `"SHA256"` і `"utf-8"` → `"UTF-8"` у `hash_password`), еквівалентні: результат хешування не змінюється, тому вбити їх неможливо.

### Тести на основі властивостей

Бібліотека: Hypothesis, файл `src/api/tests/test_properties.py`. Приклад: `test_time_overlap_is_symmetric_for_any_slots` перевіряє, що `time_overlap(a, b)` дорівнює `time_overlap(b, a)` для будь-яких двох слотів, бо перетин двох інтервалів не залежить від того, який із них названо першим.
