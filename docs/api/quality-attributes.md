# Атрибути якості API (Quality Attributes)

Документ визначає конкретні, вимірювані цілі для нефункціональних вимог проєкту та умови, за яких ціль вважається не досягнутою (провал).
Перевірка проводиться через Swagger UI (`/api-docs`) та автоматизовані тести (`src/api/tests/test_api.py`).

## PERF-001: Швидкість оновлення лічильника місць

| Елемент | Опис |
|---|---|
| **Ціль** | Лічильник вільних місць оновлюється на клієнті не пізніше ніж через 1с після успішного запису (POST `/games/{id}/players`) |
| **Умова провалу** | Час між успішною відповіддю 201 та відображенням оновленого `current_players` перевищує 1с |
| **Статус** | ✅ Реалізовано — `PlayersResponse` повертає `current_players` одразу у відповіді запиту |

## REL-001: Цілісність бронювання кімнат

| Елемент | Опис |
|---|---|
| **Ціль** | При 20 одночасних спробах забронювати один часовий слот кімнати — 0 випадків подвійного бронювання |
| **Умова провалу** | Два запити одночасно отримують успішну відповідь (201) на перетинаючі бронювання однієї кімнати |
| **Статус** | ⚠️ Частково — перевірка конфлікту (`find_busy_game`) реалізована логічно і повертає 409, але дані зберігаються в оперативній пам'яті процесу (`store.py`) без справжніх ACID-транзакцій БД. Атомарність операції не гарантована явним блокуванням — це припущення поведінки asyncio, а не перевірена гарантія. Повноцінна верифікація неможлива до переходу на реальну БД. |

## REL-002: Заборона перетину ігор майстра

| Елемент | Опис |
|---|---|
| **Ціль** | 0 успішних відповідей (409 Conflict для всіх) при спробах призначити майстра на ігри, що перетинаються в часі |
| **Умова провалу** | Хоча б 1 успішна відповідь (не 409) зі 100 спроб призначити майстра на гру, що перетинаються в часі з його іншою грою |
| **Статус** | ✅ Реалізовано — `find_busy_game` перевіряє перетин і за `room_id`, і за `master_id` |

## REL-003: Доступність системи

| Елемент | Опис |
|---|---|
| **Ціль** | Доступність не менше 99% робочого часу клубу щомісяця |
| **Умова провалу** | Сукупний простій системи перевищує ≈3,6 години за календарний місяць (доступність нижча за 99 %) |
| **Статус** | ⚠️ Не перевіряється на рівні API — залежить від інфраструктурного рівня (Cloud Infrastructure & Reverse Proxy з `high-level-design.md`), не від коду цього модуля |

## SEC-001: Хешування паролів

| Елемент | Опис |
|---|---|
| **Ціль** | 0 паролів у відкритому тексті у сховищі, коді, логах або API; паролі зберігаються виключно у хешованому вигляді |
| **Умова провалу** | Хоча б 1 пароль у відкритому тексті: у сховищі облікових даних, у коді, в логах або у відповіді API (перевірено на 3 демо-акаунтах) |
| **Статус** | ✅ Реалізовано — `hash_password` використовує PBKDF2-HMAC-SHA256 (100 000 ітерацій), `verify_password` порівнює хеші через `hmac.compare_digest` (захист від timing-атак) |

## SEC-002: Доступ до персональних даних

| Елемент | Опис |
|---|---|
| **Ціль** | Персональні дані (email, контакти) доступні лише гравцю та власнику клубу; 100% відхилення без потрібної ролі |
| **Умова провалу** | Email, password_hash або contacts з'являються у відповіді будь-якого ендпоінту |
| **Статус** | ✅ Реалізовано — підтверджено явно в `api-design.md` розділ 8: "Відповіді не містять email, password_hash, contacts"; схеми `User`/`Player` не містять цих полів |

## SEC-003: Блокування після невдалих спроб входу

| Елемент | Опис |
|---|---|
| **Ціль** | Після 5 невдалих спроб автентифікації за 15 хв акаунт блокується на 15 хв |
| **Умова провалу** | Необмежена кількість невдалих спроб входу без блокування |
| **Статус** | ✅ Реалізовано — `routes/auth.py` блокує акаунт на 15 хв після 5 невдалих спроб за 15 хв (429, `ACCOUNT_LOCKED`, `Retry-After`). Перевірено тестами `src/api/tests/test_auth_routes.py`. Обмеження: лічильники живуть у пам'яті процесу. |

## SEC-004: Відхилення реєстрації на заблокований email

| Елемент | Опис |
|---|---|
| **Ціль** | Реєстрація на email заблокованого профілю відхиляється за ≤300мс |
| **Умова провалу** | Час обробки відхилення перевищує 300мс, або реєстрація проходить успішно |
| **Статус** | ⚠️ Не застосовується в поточній версії — ендпоінту реєстрації немає взагалі (лише `/auth/login` для вже існуючих демо-акаунтів). Вимога не може бути перевірена до появи реєстрації користувачів |

## USAB-001: Швидкість реєстрації та першої заявки

| Елемент | Опис |
|---|---|
| **Ціль** | Реєстрація + подача першої заявки на гру за ≤3 хв без довідки |
| **Умова провалу** | У тестовій групі з 5 нових користувачів хоча б 1 не завершив реєстрацію і першу заявку на гру за 3 хвилини без довідки |
| **Статус** | ⚠️ Не застосовується в поточній версії — немає ендпоінту реєстрації (див. SEC-004). Юзабіліті-тест на групі користувачів неможливий до появи цього функціоналу |

## MAINT-001: Конфігурація кімнат без передеплою

| Елемент | Опис |
|---|---|
| **Ціль** | 0 змін у файлах `.py` і 0 повторних деплоїв для зміни місткості чи додавання кімнати |
| **Умова провалу** | Зміна місткості однієї кімнати або додавання кімнати потребує понад 0 змін у файлах `.py` і повторного деплою |
| **Статус** | 🔴 Умова провалу активна зараз — у `store.py` кімнати (`ROOMS`) та їхня місткість (`capacity`) хардкоджені безпосередньо в Python-словнику. `RoomPatch` дозволяє змінювати лише `is_blocked`, не `capacity`. Свідомо прийняте обмеження поточної версії — демо-дані без persistence-рівня; буде переглянуто при переході на реальну БД. |
