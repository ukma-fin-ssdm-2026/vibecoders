# Проєктування API (API Design)

API організатора настільних рольових ігор (НРІ). Специфікація OpenAPI генерується з коду (`src/api`) і не редагується вручну: `docs/api/openapi-generated.yaml`.

## 1. Принципи

- REST поверх HTTP/JSON, базовий шлях `/api/v1`.
- Code-First: джерело правди — код FastAPI + Pydantic; специфікація перегенеровується при кожному запуску сервера та при кожному push у `main`.
- Контракт зовнішній: все, що описано в специфікації, вважається обіцянкою клієнтам (віртуальний готель, фронтенд, агенти через MCP).

## 2. Модель ресурсів

Ресурси — іменники у множині, дієслів у шляхах немає. Вкладення відображає володіння.

| Ресурс | Шлях | Відповідає сутності ER-моделі |
|---|---|---|
| Ігри | `/api/v1/games`, `/api/v1/games/{game_id}` | Game |
| Гравці гри | `/api/v1/games/{game_id}/players`, `/api/v1/games/{game_id}/players/{user_id}` | GameEnrollment |
| Кімнати та календар | `/api/v1/rooms`, `/api/v1/rooms/{room_id}`, `/api/v1/rooms/calendar` | Room, Game, RoomBlock |
| Бронювання та блокування кімнати | `/api/v1/rooms/{room_id}/bookings`, `/api/v1/rooms/{room_id}/blocks` | Game, RoomBlock |
| Користувачі | `/api/v1/users`, `/api/v1/users/me`, `/api/v1/users/{user_id}` | User |
| Сповіщення | `/api/v1/notifications` | Notification поточного користувача |
| Автентифікація | `/api/v1/auth/register`, `/api/v1/auth/login` | User, Token |

Профіль користувача доступний лише самому незаблокованому користувачу та власнику клубу (SEC-002). Пароль і його хеш ніколи не повертаються.

## 4. Семантика HTTP-методів

| Метод | Безпечний | Ідемпотентний | Примітка |
|---|---|---|---|
| GET | так | так | Не змінює стан |
| POST | ні | ні | Повторний запис на гру дає 409, а не дубль; `login` не створює ресурс, тому повертає 200 |
| PUT | ні | так | Усі поля обов'язкові; відсутнє поле — 400 |
| PATCH | ні | не гарантовано | Змінює лише передані поля; порожнє тіло — 400 |
| DELETE | ні | стан так, відповідь ні | Перший виклик 204, повторний 404; стан системи однаковий |

PUT повністю замінює ігровий ресурс, тому часткове тіло відхиляється. Для часткових змін існує PATCH.

## 5. Коди статусів

| Код | Коли |
|---|---|
| 200 | Читання та успішне оновлення |
| 201 | Створено гру, запис гравця, акаунт або блокування кімнати; заголовок `Location` вказує на ресурс |
| 204 | Видалення без тіла відповіді |
| 400 | Вхідні дані не пройшли валідацію (типи, діапазони, формат id, невідомі поля, порожній PATCH) |
| 401 | Немає токена або він недійсний |
| 403 | Токен дійсний, але роль не дозволяє дію або акаунт заблоковано |
| 404 | Гру, кімнату, користувача, блокування або запис не знайдено |
| 409 | Дані валідні, але суперечать стану: конфлікт блокувань, існуюча пошта, спроба заблокувати себе, кімната/майстер зайняті, немає місць |
| 429 | Акаунт заблоковано на 15 хвилин після 5 невдалих спроб входу за 15 хвилин. Заголовок `Retry-After` містить кількість секунд до розблокування |
| 500 | Непередбачена помилка сервера |

Код 422, який FastAPI повертає за замовчуванням, свідомо замінено на 400, щоб усі помилки валідації мали однаковий код і формат.

## 6. Структура помилок

Усі помилки (включно з неіснуючими шляхами та 500) мають одну форму:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Вхідні дані не пройшли валідацію",
    "details": [
      {"field": "body.max_players", "message": "Input should be less than or equal to 8"}
    ]
  }
}
```

`code` — стабільний машинозчитуваний рядок (клієнт перемикається по ньому), `message` — текст для людини, `details` — список проблемних полів (порожній, якщо неактуально). Коди: `VALIDATION_ERROR`, `UNAUTHORIZED`, `FORBIDDEN`, `GAME_NOT_FOUND`, `ROOM_NOT_FOUND`, `USER_NOT_FOUND`, `ROOM_BLOCK_NOT_FOUND`, `ENROLLMENT_NOT_FOUND`, `ROOM_BUSY`, `ROOM_BLOCKED`, `ROOM_BLOCK_CONFLICT`, `MASTER_BUSY`, `ROOM_CAPACITY_EXCEEDED`, `MAX_PLAYERS_BELOW_ENROLLED`, `GAME_FULL`, `ALREADY_ENROLLED`, `INVALID_CREDENTIALS`, `EMAIL_ALREADY_REGISTERED`, `USER_BLOCKED`, `CANNOT_BLOCK_SELF`, `ROOM_HAS_GAMES`, `ACCOUNT_LOCKED`, `INTERNAL_ERROR`.

## 7. Пагінація, фільтри, порядок

- Параметри `limit` (1–100, за замовчуванням 20) та `offset` (≥ 0).
- Відповідь: `{"items": [...], "pagination": {"limit", "offset", "total", "has_more"}}`.
- Порядок у списку ігор гарантований контрактом: за `starts_at` за зростанням, потім за `id`. Клієнти можуть спиратися на це.
- Фільтри `room_id` та `master_id` комбінуються через AND.

## 8. Безпека

- Реєстрація: `POST /auth/register` створює акаунт із роллю `player`, зберігає пароль лише як PBKDF2-хеш і повертає випадковий Bearer-токен. Пошта нормалізується до нижнього регістру; повторна поштова адреса, у тому числі заблокованого профілю, повертає 409 `EMAIL_ALREADY_REGISTERED`.
- Вхід: `POST /auth/login` з поштою та паролем повертає токен. Пароль перевіряється за хешем (PBKDF2), у відповідях і логах не зʼявляється. Помилка однакова для невідомої пошти та хибного пароля, щоб не розкривати, які акаунти існують. Заблокований власником профіль не може увійти (403 `USER_BLOCKED`).
- Схема: HTTP Bearer. У цій версії токени — заглушки: `master-token`, `player-token`, `owner-token`; демо-акаунти: `master@club.test`, `player@club.test`, `owner@club.test`.
- Блокування акаунта: лише власник може змінювати `is_blocked`. Блокування анулює токени; будь-який захищений запит такого користувача відхиляється. Розблокування не відновлює попередні токени.
- Приватність профілю: `GET /users/{user_id}` із контактами, аватаром та історією записів доступний лише самому незаблокованому користувачу або власнику. Відповідь не містить `password_hash`.
- Обмеження спроб входу (SEC-003): після 5 невдалих спроб за 15 хвилин акаунт блокується на 15 хвилин. Під час блокування `POST /auth/login` повертає 429 з кодом `ACCOUNT_LOCKED` і заголовком `Retry-After`, навіть якщо пароль правильний. Невдалі спроби старші за 15 хвилин не враховуються, успішний вхід скидає лічильник. Невідома пошта блокується так само, як відома. Лічильники зберігаються в пам'яті процесу і скидаються при перезапуску; перенесення до справжнього сховища користувачів заплановане.
- Читання ігор і кімнат відкрите. Список гравців, створення, зміна, видалення та запис потребують токена.
- Читання повного календаря відкрите. Створення/видалення періоду блокування кімнати та блокування акаунтів доступні лише власнику.
- `/users/me` змінює лише профіль поточного токена. `PATCH` приймає непорожній набір полів; `null` очищує контакти або URL аватара, але не ім'я. `/users` повертає лише публічні поля (id, ім'я, роль і стан блокування), відсортовані за id.
- `GET /notifications` повертає лише записи користувача, що відповідає Bearer-токену, у порядку від найновішого. Маршрут не приймає user id від клієнта.
- Права:

| Дія | player | master | owner |
|---|---|---|---|
| Створити гру | ні | так | так |
| Змінити або видалити гру | ні | лише свою | будь-яку |
| Записатися на гру | так | так | так |
| Скасувати запис | лише свій | у своїй грі | будь-який |
| Переглянути персональний профіль | лише свій | лише свій | будь-який |
| Редагувати власний профіль | так | так | так |
| Переглянути список користувачів | ні | ні | так |
| Переглянути сповіщення | лише свої | лише свої | лише свої |
| Заблокувати кімнату на період | ні | ні | так |
| Заблокувати користувача | ні | ні | так |

- Валідація авторизації виконується на кожному запиті до ресурсу, а не лише на вході.
- Email і контакти повертаються лише у дозволеному профілі; `password_hash` та токени не повертаються ніколи.
- Під час блокування кімнати фіксується період `[starts_at, ends_at)`. Усі ігри, що перетинають цей інтервал, скасовуються в межах тієї самої транзакції, а записані гравці отримують системне сповіщення. Створення гри з перетином періоду повертає 409 `ROOM_BLOCKED`. Видалення періоду не відновлює скасовані ігри.

## 9. Версіонування

- Версія у шляху: `/api/v1`. Поле `info.version` специфікації — семантична версія (1.0.0).
- Допустимі зміни в межах v1 (зворотно сумісні): нове необов'язкове поле у відповіді, нова кінцева точка, новий необов'язковий параметр запиту, новий код помилки.
- Ламаючі зміни (видалення або перейменування поля, зміна типу, нове обов'язкове поле у запиті, зміна семантики коду статусу) — тільки у `/api/v2`. Стара версія живе паралельно та позначається `deprecated` у специфікації мінімум один семестровий цикл.

## 10. Антипатерни, яких уникаємо

| Антипатерн | Як у нас |
|---|---|
| Дієслова у шляхах (`/getGames`) | Іменники у множині |
| `200 OK` із помилкою в тілі | Код статусу відповідає змісту |
| Різні формати помилок | Один `ErrorResponse` |
| Незадокументований порядок у списках | Порядок зафіксовано (розділ 7) |
| Привʼязка шляху до провайдера або реалізації | Нейтральні назви ресурсів |
| Список без пагінації | `limit`/`offset` у всіх списках |
| Довіра до id з шляху без перевірки прав | Перевірка ролі та власника на кожній зміні |
| Повторне використання id після видалення | Лічильник id тільки зростає |

## 11. Узгодженість із кодом

Перевіряється автоматично тестами `src/api/tests/test_spec.py` (кожна кінцева точка має summary, description і описані 4xx, `test_every_operation_has_summary_description_and_documented_4xx`) та `src/api/tests/test_quality_goals.py` (збіг закоміченого `openapi-generated.yaml` зі специфікацією з коду); формат помилок єдиний, коди статусів відповідають таблиці розділу 5.
